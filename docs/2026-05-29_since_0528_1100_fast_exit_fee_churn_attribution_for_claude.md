## 9. 是否"只是在给 Binance 送手续费"

### 9.1 严格按本窗口成交回报

- **不是纯送手续费**：`已实现 PnL = +2.45905699 USDT`，窗口内为正。
- **但手续费磨损是真实存在的**：
  - 手续费 `-0.00197514 BNB`
  - 265 fills / 79 orders 对约 98~99 USDT 权益账户而言，**换手率偏高**
  - 若 BNBUSDT 约为 600 USDT，则手续费约折算 **1.19 USDT**，真实净 PnL 约为 **+1.27 USDT**
- **权益曲线来看**：从最高约 `99.67 USDT` 回落至 `98.48 USDT`，用户体感"回吐"成立

### 9.2 更准确的表述

> 当前退出栈不是每笔都亏，但它把账户推向高频碎片化交易。只要短线信号优势略微下降，手续费 + 滑点 + 残仓清理 + 50% reduce 叠加后，很容易把 gross edge 全部磨损掉。**当前系统处于"细线上跳舞"的状态**。

## 10. 问题机制深度解析

### 10.1 `fast_fail(age=2bars)` 过早接管

典型审计记录：

```text
BETA_RISK_CLOSE:
  alt_15m_against(0.971%)
  alt_30m_against(0.762%)
  btc_15m_against(0.238%, corr=0.62)
  fast_fail(age=2bars, mfe=0.179%, mae=-0.790%)
```

**问题分析**：

- `age=2bars` = 仅持仓 2 根 15m K 线（约 30 分钟）即触发判定
- MFE 仅 0.179%（未达 0.2% 阈值），MAE 已到 -0.790%
- 这套逻辑**适合极短线防守**（scalping 场景），但不适合 1h/4h 共振兑现策略
- Quadrant / MACD 信号通常需要 1~4 小时才能完整兑现，fast_fail 在此之前已强制退出

### 10.2 `BETA_RISK_REDUCE/CLOSE` 与策略持仓周期的根本性冲突

| 维度 | 策略设计意图 | btc_beta_risk 实际行为 |
|---|---|---|
| 信号周期 | 1h / 4h 共振 | 15m / 30m 反向即触发 |
| 持仓期望 | 等待趋势兑现 | 入场后 2 根 bar 判定失败 |
| 退出逻辑 | TP/SL 或技术性退出 | 风险评分触发强制减仓/全平 |
| 结果 | 捕捉中短周期利润 | 被压缩成 scalping 系统 |

### 10.3 `small_notional_close_threshold=10U` 在小账户下的结构性问题

账户权益约 98~99 USDT，典型持仓链条：

```text
初始仓位（约 30~60U）
  `-- 触发 BETA_RISK_REDUCE（50% 减仓）-> 残仓约 15~30U
      `-- 再次触发 BETA_RISK_REDUCE（50% 减仓）-> 残仓约 7~15U
          `-- 残仓 < 10U -> small_notional_close -> 手续费 x N
```

这不是传统风控止损，而是**仓位碎片化导致的交易成本放大**。阈值 10U 对于 100U 账户来说，占比 10%，过高。

### 10.4 审计 `pending` 大量未闭环

close/reduce 的 post_execution 状态分布：

| 状态 | 数量 |
|---|---:|
| pending | **43** |
| success | 10 |

超过 80% 的退出审计处于 `pending` 状态，说明订单生命周期没有在审计层完整闭环。这会导致：
- 同一轮退出被误读为多次独立策略行为
- 手续费和 realized PnL 在审计层统计不完整
- 后续参数优化依赖不完整数据，存在误导风险

## 11. 建议评审问题清单

### 高优先级（直接影响现有 edge 是否能存活）

1. **`fast_fail_window_bars=2` 是否过短？**  
   是否应调整为更长观察期（如 4~6 bars），或增加最小持仓时间（如 45~60 分钟），避免在 15~30 分钟内过早否定 1h/4h 信号？

2. **`fast_fail_mae_threshold=-0.2%` 和 `fast_fail_mfe_threshold=0.2%` 的标准是否过于敏感？**  
   对小币种（波动率高）和 3x 杠杆账户而言，0.2% 的阈值是否足以区分"信号失败"与"正常市场噪声"？

3. **`small_notional_close_threshold=10U` 是否应动态缩放？**  
   对于 100U 账户，10U 占 10% 权益；是否应按以下方式动态设定：
   - `max(交易所最小名义额, 账户权益 x 1%~2%)` ？

4. **0.00U / 0.01U / 0.11U 级别的残仓是否应禁止进入真实下单？**  
   对这类残仓只做本地状态清理，不产生实际 Binance API 请求。

### 中优先级（优化 edge 质量）

5. **`risk_score_reduce_threshold=2` 的 50% reduce 是否应增加净收益护栏？**  
   要求触发 reduce 前，当前浮盈扣除本次手续费后仍为正值，否则推迟执行。

6. **同一 symbol 同一时间的多笔 reduce/close 是否应合并？**  
   将相邻时间窗口（如 +/-1 bar）内同 symbol 的退出意图合并为单次 close intent，减少订单碎片。

7. **`alt_against_15m_pct=-0.1%` 是否过于敏感？**  
   15 分钟内 0.1% 的反向动作是否足够作为风险信号，还是只是正常的盘中噪声？

### 基础设施优先级

8. **审计 `pending` 状态是否需要在成交回报落地后回填？**  
   应在 `trade_fills_utc.csv` 确认成交后，将审计记录中对应的 `pending` 更新为最终成交状态、手续费和 realized PnL，以保证后续归因数据完整性。

## 12. 建议验证方案

### 12.1 先做只读重放，不直接改 live 配置

对同一时间窗口做四组 replay 对比：

| 方案 | 核心变化 | 预期观测 |
|---|---|---|
| **Baseline** | 当前配置，零变化 | 复现 265 fills 换手行为 |
| **Treatment A** | 关闭 `fast_fail`，保留普通 beta reduce/close | 观察持仓时长分布变化和手续费变化 |
| **Treatment B** | 保留 `fast_fail`，`fast_fail_window_bars` 从 2 -> 4，MAE 要求更深 | 观察短周期退出减少比例和 PnL 影响 |
| **Treatment C** | 禁用 `small_notional_close` 低于交易所有效最小名义额的真实下单 | 观察碎片化平仓次数减少和手续费节省 |

### 12.2 必须报告的对比指标

**收益类**：
- Sharpe Ratio
- Profit Factor
- Win Rate（总体 / <=30min 子集 / >30min 子集）
- Expectancy（每笔期望盈亏）
- Max Drawdown（按权益曲线）

**交易行为类**：
- 总成交笔数 / 订单数
- 平均持仓时间
- <=30 分钟退出占比
- small_notional_close 触发次数
- 50% reduce 触发次数

**成本类**：
- 手续费（BNB 总量 + 折算 USDT）
- 平均滑点估计
- Exposure（平均仓位占权益比）

**风险类**：
- Tail Risk（P5 单笔亏损分位）
- MFE/MAE 分布
- 最大连续亏损笔数

### 12.3 防未来函数与成交假设（必须遵守）

- Replay 不允许使用信号 bar 后的行情判断当前退出决策
- 退出成交不能假设同 bar 理想价格，必须加入滑点和延迟模拟
- Binance 成交回报可作为真实成交事实，回测对照必须加入**手续费 + 滑点 + 延迟**
- **严禁只按 2026-05-28 单窗口调参**，否则过拟合风险极高；参数变化必须在至少 2 周历史窗口上验证

## 13. 最终归因结论

### 13.1 一句话归因

> 本窗口的高频退出和权益回撤，主要不是传统止盈止损参数错误，而是 `btc_beta_risk` 在小账户（~100U）、小仓位、15m/30m 噪声环境下**过度接管退出**，形成"快速失败（2 bars）-> 50% 减仓 -> 小额残仓清理（<10U）"的高换手链条；这条链条在短线 edge 变弱时，将非常容易把账户变成给交易所贡献手续费和滑点的机器。

### 13.2 系统性风险评级

| 维度 | 当前状态 | 风险等级 |
|---|---|---|
| 退出栈敏感度 | `fast_fail_window_bars=2`，阈值 +/-0.2% | 高 |
| 碎片化平仓 | 0.00U~8.83U 残仓进入真实下单 | 高 |
| 审计数据完整性 | 80%+ pending 未闭环 | 中 |
| 传统 TP/SL 合理性 | 本窗口未触发，暂无负面证据 | 低 |
| 短线盈利可持续性 | 依赖少数赢家，edge 细薄 | 中 |

### 13.3 最高优先级行动建议

1. **立即评估**：将 `small_notional_close` 的真实下单禁止条件设置为"低于交易所 minimum notional"，仅做本地状态清理
2. **短期验证**：对 `fast_fail_window_bars` 做 2 -> 4 的 replay 对比，在不改 live 配置的前提下量化持仓时长和手续费变化
3. **中期优化**：将 `small_notional_close_threshold` 改为动态计算：`max(MIN_NOTIONAL_EXCHANGE, equity x 0.02)`
4. **持续监控**：在审计系统中补充 pending -> success 的回填机制，确保后续归因数据可信
