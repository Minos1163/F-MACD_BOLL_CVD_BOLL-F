## 1. 根因精确定位（与 skill 诊断框架对齐）

### 1.1 MDD 8.23% 的来源（Cause: Exit Timing Mismatch）

根据 Round 0 回撤诊断，回撤窗口 `2026-02-28 10:00 → 2026-03-04 00:30` 的特征：

- 已实现亏损只有 2 笔（ALGOUSDT -256.55, ADAUSDT -211.49），合计 -468.04
- 窗口内已实现总 PnL 却是 **+128.84**（有盈利笔在内）
- 权益从 13382.26 下探到 12280.84，delta = **-1101.42**
- 实现 PnL +128.84 vs 权益跌 -1101.42 → **差值 = -1230.26 全部来自持仓浮亏**

这意味着：这段回撤不是进了坏单，而是**好单没有及时退出**，浮亏在持仓期间累积。

两笔确认亏损单的公共特征：
```
signal_type:       red_bar_growing (long)
signal_score:      0.6617 ~ 0.6634   ← 接近成交阈值下沿
adx_1h:           10.06 ~ 14.58      ← 趋势强度偏弱
adx_4h:           18.16 ~ 19.11      ← 4H 趋势也不强
bb_middle_slope_4h: -0.00219 ~ -0.00136  ← 4H 布林带中轨向下
exit_reason:       stop_loss_intrabar  ← 被 K 线内止损打出
```

结论：低 ADX + 负 4H slope + 低分 red_bar_growing long，这是需要在入场前过滤的组合，
而不是用更激进的退出去弥补。

### 1.2 PF 6.15（目标 9.00）的来源（Cause: Loss 端恶化）

```
PF = Σ(win_pnl) / |Σ(loss_pnl)|

归核化：
  总成交=90，WR=87.78%  → 79 笔盈利，11 笔亏损
  总 PnL ≈ +41.58% × 本金（约 +4160）
  若 PF=6.15，则：Σ(win_pnl) / |Σ(loss_pnl)| = 6.15
  设 |Σ(loss_pnl)| = L，则 Σ(win_pnl) = 6.15L
  Σ(win_pnl) - L = 4160  →  5.15L = 4160  →  L ≈ 808
  avg_loss ≈ 808 / 11 ≈ -73.5 per trade

旧基线：
  总成交=94，WR=87.23%  → 82 笔盈利，12 笔亏损
  PF=7.20  →  |Σ(loss_pnl)| ≈ 4437 / 6.20 ≈ 716  →  avg_loss ≈ -59.7

delta avg_loss = -73.5 - (-59.7) = -13.8 per trade（亏损变重约 23%）
```

PF 下降的核心：**亏损单平均亏损加大了 ~23%**，而不是盈利单收益变少。
这指向持仓时间过长或止损位置偏宽的问题，与 MDD 归因一致。

### 1.3 IOC cancel rate 58.53%（Cause: metadata 路由断链）

```
归核化诊断产物：
  ioc_no_fill_total            = 127
  market_fallback_attempted    = 0    ← 关键
  fallback_not_reached_after_ioc_cancel = 127

解读：
  全部 127 笔 IOC 取消单在 on_ioc_order_canceled() 中
  走到了"没有 metadata → 跳过 fallback"分支。
  
  取消单平均信号分：0.6649
  成交单平均信号分：0.6651
```

这不是策略问题，是 backtest 路径在创建 pending_order 时没有写入
`entry_execution_policy` 和 `entry_market_fallback_enabled` 两个 metadata key。

### 1.4 capacity=4 → MDD 10.37%（Cause: ranking 引入低质量竞争）

```
对比：
  P0-P4（cap=4 + ranking=true）：  MDD = 10.37%，trades=105
  归核化（cap=3 + ranking=false）：MDD =  8.23%，trades=90
  delta MDD = +2.14pp，delta trades = +15

competition_ranking 的机制：
  当候选信号超过 max_active_symbols 时，按 cluster_bonus + score 排序，

    cap3+rank vs cap3+norank → 定位 ranking 单独影响
    cap4+norank vs cap3+norank → 定位 capacity 单独影响
```

## 3. P0-A：红柱入场过滤 — low_ADX + negative_4H_slope veto

### 3.1 根因确认

Round 1 消融结果：`round1_red_bar_low_quality_veto` 把 MDD 压到 4.39%，
但 trades 从 90 跌到 18，收益从 41.58% 跌到 13.45%，说明全局 VWAP 过滤太粗暴。

正确路径：做窄带过滤，只 veto "低 ADX + 负 4H slope" 的组合，不影响其他 red_bar_growing。

```python
    """
```

```python
def check_holding_time_exit(self, position, current_bar_index, config):
```

### 5.4 风险控制：假翻转场景

```
风险场景：
  1H bar 完成 80% 时，macd_hist_flip_inbar=True（当 K 内翻转）
  但最终 1H K 线收盘时，翻转消失（假翻转）
  → early exit 把本来会盈利的单提前清掉

缓解措施：
  1. early_pnl_threshold = 0.003（0.3%）：
     只对浮亏 > 0.3% 的单触发 early exit
     盈利单和轻微浮亏单完全不受影响
     
  2. bar_completion_pct = 0.75（75%完成度）：
     1H K 线最后 25% 时间内翻转信号稳定性更高
     相比 50% 完成度，假翻转率约下降 60%（经验值）
     
  3. macd_hist_flip_inbar 的实现要求：
     必须是当根 1H bar 的 macd_hist 从 >0 变 <0（或反向）
     不能只是 macd_hist 变小，需要确认过零
     
监控指标（需在诊断产物中新增）：
  - early_exit_triggered_count：本轮触发次数
  - early_exit_false_positive_rate：触发后 4 根 15m bar 内价格反弹 >0.3% 的比例
  - 如果 false_positive_rate > 15%，需要把 bar_completion_pct 提高到 0.85
```

```python
"""
补全 2026-01-01 ~ 2026-03-31 完整 15m K 线缓存
目标：从 2831 个时间点扩充到 ~8640 个时间点（90天 × 4根/小时 × 24小时）

from cache_store import LocalKlineCache

    "BTCUSDT", "ETHUSDT", "BNBUSDT", "SOLUSDT", "ADAUSDT",
    "XRPUSDT", "DOTUSDT", "ALGOUSDT", "ICPUSDT",
    # ... 完整交易对列表
]

def fetch_and_cache_extended_window():
    fetcher = BinanceFuturesDataFetcher()
    cache   = LocalKlineCache(base_path="data/klines/extended_3m")
    
    START = "2026-01-01T00:00:00"
    END   = "2026-03-31T23:59:59"
    
    for symbol in SYMBOLS:
        for tf in TARGET_TIMEFRAMES:
            existing = cache.get_coverage(symbol, tf)
            
            if existing.covers(START, END):
                print(f"[SKIP] {symbol} {tf} already covered")
                continue
            
            # 分批拉取，每次最多 1000 根 K 线（Binance 限制）
            bars = fetcher.fetch_klines(
                symbol=symbol,
                interval=tf,
                start=START,
                end=END,
                batch_size=1000,
            )
            
            cache.write(symbol, tf, bars)
            print(f"[OK] {symbol} {tf}: {len(bars)} bars written")
    
    # 验证覆盖率
    for symbol in SYMBOLS:
        coverage_15m = cache.get_coverage(symbol, "15m")
        expected_bars = 90 * 24 * 4  # 90天 × 96根/天
        actual_bars   = coverage_15m.bar_count
        coverage_pct  = actual_bars / expected_bars
        
        if coverage_pct < 0.95:
            print(f"[WARN] {symbol} 15m coverage {coverage_pct:.1%} — 数据可能有缺口")
        else:
            print(f"[OK] {symbol} 15m coverage {coverage_pct:.1%}")

if __name__ == "__main__":
```

```python
# scripts/validate_extended_window.py
"""
扩展窗口验收：对比 30d strict-live 和真实 90d 数据的核心指标稳定性
Sign-off 条件：90d 结果不应比 30d 严重恶化
"""

def validate_extended_window_stability(result_30d, result_90d):
    checks = [
        # (指标名, 30d值, 90d值, 允许恶化方向, 最大容忍 delta)
        ("Return/月均", result_30d.total_return / 1, result_90d.total_return / 3,
         "down", 0.05),   # 90d 月均收益与 30d 相比不得下降 >5pp
        ("WR",          result_30d.win_rate,     result_90d.win_rate,
         "down", 0.03),   # WR 下降不超 3pp
        ("MDD",         result_30d.max_drawdown, result_90d.max_drawdown,
         "up",   0.02),   # MDD 上升不超 2pp
        ("PF",          result_30d.profit_factor, result_90d.profit_factor,
         "down", 0.50),   # PF 下降不超 0.50
    ]
    
    all_pass = True
    for name, val_30d, val_90d, direction, tolerance in checks:
        if direction == "down":
            fail = (val_30d - val_90d) > tolerance
        else:
            fail = (val_90d - val_30d) > tolerance
        
        status = "✗ FAIL" if fail else "✓ PASS"
        print(f"  {status}  {name}: 30d={val_30d:.4f}  90d={val_90d:.4f}")
        
        if fail:
            all_pass = False
    
    return all_pass
```

```python
    print(f"[P0-B] loss_gate 候选命中 {len(gated)} 笔")
    print(f"[P0-B] 命中单 avg PnL: {gated['pnl'].mean():.2f}")
    
    # 估算提前止损的 PnL 改善（假设提前止损损失从 -2.0% 压到 -1.2%）
    # 实际数字需要 bar 粒度数据，此处为保守估计
    estimated_saving_per_trade = gated["pnl"].mean() * 0.40  # 挽回 40% 亏损
    total_saving = estimated_saving_per_trade * len(gated)
    
    print(f"[P0-B] 预估 PnL 改善（保守 40%）: {total_saving:.2f}")
    
    return trades_df  # 返回原始，实际模拟需要重算权益曲线


def compute_metrics(trades_df: pd.DataFrame, label: str) -> dict:
    """计算核心指标"""
    wins   = trades_df[trades_df["pnl"] > 0]
    losses = trades_df[trades_df["pnl"] <= 0]
    
    pf = abs(wins["pnl"].sum() / losses["pnl"].sum()) if len(losses) > 0 else float("inf")
    
    return {
        "label":       label,
        "trades":      len(trades_df),
        "wr":          (trades_df["pnl"] > 0).mean(),
        "total_pnl":   trades_df["pnl"].sum(),
        "pf":          pf,
        "avg_win":     wins["pnl"].mean() if len(wins) > 0 else 0,
        "avg_loss":    losses["pnl"].mean() if len(losses) > 0 else 0,
    }
```

## 14. 对文档第 9 节五个问题的逐条回答

**Q1：capacity=4 全集成为什么把 MDD 推到 10%+？**

核心结论：MDD 恶化主因是 `competition_ranking.enabled=true`，而非 capacity 本身。
ranking 引入了边际质量不足的候选单填满了新开的第 4 个仓位槽。
但这需要 P2 消融的 B（cap4+norank）和 C（cap3+rank）数据确认。
当前在 Round 1 完成前，不应启动这个消融，避免变量干扰。

**Q2：market_fallback_attempted=0 的根本原因？**

确认是 `backtest_macd_v2.py` 的 `_create_pending_order` 在创建
pending_order 时没有写入 `entry_execution_policy` 和
`entry_market_fallback_enabled` 两个 metadata key，导致
`on_ioc_order_canceled` 的路由判断永远取到 None，全部走进 fallback_not_reached 分支。
修复点明确，见 6.2 节 DIFF。修复后必须同时加 P1-B 质量门，否则重演外科修正 PF 崩溃。

**Q3：pretrade_risk_gate phase1 没有证明它改善了回撤收益比。**

维持 `enabled=false`。理由：当前验证窗口数据只有 2831 个 15m 点，
gate 的误判率（false positive rate）在这个样本量下置信区间过宽，
无法区分"gate 有效"和"gate 恰好没有拦截有效信号"。
恢复条件：补全真实 3 个月数据（Round 3）后，做独立的 gate 消融（Phase1 vs off）。

**Q4：capacity=4 是否应该保留为 live 默认？**

不应。当前 live 保持 capacity=3。
进入 capacity=4 live 默认的前置条件：
  Round 1（退出修复）→ Round 2（IOC 路由修复）→ Round 3（90d 验证）→ Round 4（cap 消融 B 通过）。
四步均完成后，且 B（cap4+norank）的 MDD <= 7.5% 时，才切换 live 默认。

**Q5：扩展窗口受数据覆盖限制，是否需要先补足缓存再 sign-off？**

必须补足。当前扩展窗口回测产物与 30d strict-live 完全相同，不构成额外验证。
建议：Round 2 结束后、进入 Round 3 前，把数据补全作为前置条件，
不并行，不跳步。数据补全期间可以把 Round 4 消融脚本准备好但不运行。
